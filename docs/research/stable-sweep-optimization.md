# stable 整屏扫动与白线复核

日期：2026-10-08。用户复现条件：本机安装的 stable、16×12、15 FPS、60 Hz，整屏扫动并闪白线。基线为本次修改前的 `HEAD`（`osu_paint_video.py` blob `98839fd`）。所有测试画面均为合成输入，没有读取或提交个人视频。

## 可复现的原因

12 行并不意味着启用长条后一定能缩短清场。16 列图案只要在各行都有短音符或长条端点，当前 stable 模型仍需 12 个不同整数时间戳，另留一个清场槽，共 13 ms。本机游戏 SHA-256 仍为 `3adc2d001aacced5f92ba8ae24121980d5e23f5653f37d14cf4765bca1abd9f9`，与此前整数解析、MovementY 和滚速证据一致，见 [stable 时间证据](stable-timing.md)。本轮只读核查缓存调用链及安装文件哈希，没有修改游戏或配置。

原排帧把每次 13 ms 清场都限制在同一个 16.667 ms 刷新间隔内，结束时刻可移动的余量只有约 3.667 ms。这样的长区间存在共同覆盖的相位；仅加快余量范围内的折返，也无法使这些相位避开扫屏。15 FPS 的一幅图占四次 60 Hz 刷新，降低视频 FPS 会增加静置时间，但不会自动缩短这 13 ms。

最小回归素材：第一列持续全黑，其余十五列按行交替黑白，下一幅反转后十五列，共 65 幅。它强制保留十二个端点行，也能用第一列检查新旧画面之间的白带。运行：

```powershell
.\.build-env\Scripts\python.exe -m unittest discover -s tests -p test_stable_sweep_phase.py -v
```

新增第一项回归在修改前失败：`64 not less than 64`，最坏相位总命中与最长连续命中均为 64。独立重解析 `.osu` 积分，在名义换帧前 4 ms、8 ms 的固定采样相位，64 次都出现内部白带，最大约 2.000507 个 768 高度内部像素。这里统计的是两段可见黑块之间的间隙，排除了静置时底部约 1 像素的安全余量。

白带主要来自模型中为清场保留的画面间距，不能靠把已经不透明纯黑的 PNG 再涂黑消除。本轮保留这一间距，避免未经原生裁剪和 GPU 验收就缩小安全余量后留下旧音符。

## 搜索核查的机制

| 机制 | 一手依据与本轮判断 |
| --- | --- |
| 固定滚速、参考 BPM、整数头尾与移动端点 | 本机程序集及既有原生反射结果；本轮哈希一致。绿线不能解除整数端点限制，也不能把所有十二行直接塞进同一毫秒。 |
| 长条拉伸、Miss 颜色 | 官方皮肤文档列出 `NoteBodyStyle`，本机调用链区分拉伸与重复绘制。已有皮肤使用拉伸；本机音符 Miss 路径把颜色乘算到灰色，不能据此认定不透明纯黑会变成白带。没有新增 GPU 采样结论。 |
| 皮肤动画帧率与 `ColourHold` | 官方 `skin.ini` 文档中的前者控制贴图动画，后者控制长条期间的连击计数器颜色；都不是滚动动画或长条透明度开关。[1] |
| VSync、撕裂和帧率限制 | 官方性能文档说明 VSync 消除撕裂但引入约 1–2 帧延迟；推荐一般先用全屏与 Optimal 作为排查基线。此处是观影任务，若剩余症状是横向撕裂，可以手动对照 VSync，但它不能消除同一渲染帧内已存在的白带或保证避开 13 ms 扫屏。程序不改系统或游戏设置。[2] |
| 反向 SV、负 BPM 等非常规跳跃 | 官方问题库记录了反向 SV 技巧在 `20250628` 更新后行为改变及社区绕法。这是版本相关行为的报告，不是可靠的逐帧瞬移接口；本轮没有引入非法数值、负速或修改客户端来规避端点限制。[3] |
| 显示器拖尾 | 用户描述和合成几何足以复现扫屏及白带，但不能诊断显示器像素响应。软件积分、截图和 GPU 实机拍屏是不同证据，本轮没有实机拍屏。 |

## 实现与代价

在原来的候选之后，stable 仅在以下条件下多编译一次：实际清场大于半个刷新周期且小于一个周期，并且内容周期扣除两个刷新周期后还能容纳原排帧预算和至少 1 ms 展示。

这个候选按实际重绘组把切帧结束时刻放进接近完整刷新周期的折返范围。向下取整后，画面最多提前不到一个刷新周期，60 Hz 时小于 16.667 ms；切帧开始可以跨过前一次名义刷新，因此那次刷新可能已见到过渡或新图。重新编译后仍检查推进晚于前两次名义刷新。

采用门槛：最坏总命中、最长连续命中都严格减少；音符数和内部总过渡时长不增加；相邻画面开始间隔相对名义周期偏差不超过 1 ms。首画面、片尾、分辨率、实际 FPS、原始音轨起点都保留。条件不满足或无收益则回退，长于整个刷新周期的清场不走这条路径。包括原有候选在内，此分支最多五次核心编译；其他路径仍最多四次。

这是提前部分画面以分散坏相位的取舍，不是声画精确锁相。已有 JSON 不自动重排，使用新安排须重新导入原视频。界面没有新增相位控制或内部候选参数。

## 对照结果

以下均为上述 16×12、15 FPS、60 Hz、2000 ms 开始、启用长条的同一素材：

| 指标 | 旧 | 新 |
| --- | ---: | ---: |
| 最坏固定相位命中 / 64 次换帧 | 64 | 54 |
| 最长连续命中 | 64 | 53 |
| 名义换帧前 4 ms，相位采到内部白带的次数 | 64 | 13 |
| 名义换帧前 8 ms，相位采到内部白带的次数 | 64 | 30 |
| 名义换帧前 12 ms，相位采到内部白带的次数 | 43 | 45 |
| 内部总过渡时间 | 832 ms | 832 ms |
| 音符数 | 5915 | 5915 |
| 最大帧间隔偏差 | 0.667 ms | 0.667 ms |

最坏情况改善不代表每个相位都会改善，前 12 ms 的例子明确保留了反例。扫屏仍为 13 ms；白带宽度基本不变。总过渡时间不变，也就没有降低该合成片段在连续时间上的过渡占比，不能据此宣称残影消失。

132 组合成差分覆盖 6/9/12/15/24 行，10/15/20/30 FPS，60、60000/1001、75、90、120 Hz，以及随机种子 `20261008` 的混合图案、重复帧、空白帧、小数起点和长条开关：37 组改善，95 组序列化谱面不变。没有增加最坏总命中、最长连续命中、总过渡时长或音符数；首尾和视频元数据一致。脚本和结果位于忽略目录 `build/stable-sweep-research/compare.py`、`comparison.json`。

回归还核对序列化音符在名义刷新时刻的位置、头部仍在未来、提前范围、帧节奏、音轨起点，以及增加过渡时长时的拒绝和无时间余量时的回退。完整 233 项测试通过，按 `build_desktop.ps1` 重建桌面程序；包内五个模块与源码逐项匹配，包内编译器复现 `(54, 832, 53)` 的相位评分，两端均导出正确的 16:10 文件名与 12 行内部名称，内置 FFmpeg 保留。日志和包核对结果位于 `build/stable-sweep-research/`。16:10 默认皮肤文件名同时补齐 `-16x10`，内部名称仍含比例和实际行数；重建了全部十个根目录交付皮肤。
