# stable / lazer 刷新约束、长条与规避

核查日期：2026-09-30。保留原版 stable，并为 stable / lazer 增加实际刷新率排帧和可选的连续单键转长条。不生成专属皮肤或内容预设，预览不按理想刷新采样隐藏过渡。下方旧整数游戏 FPS 方案及产物仅作为历史记录。

## 版本和证据

本机 `osu!.exe` 文件版本 `1.3.3.8`，安装配置记录 `b20260412.1`，SHA256：`C7B77C2F6FC458521114E06C197749601651E1BD4FEEBE503F457232702B16AB`。局部反编译材料保存在忽略的 `build/stable-diagnostics/`，没有读取或上传登录凭据。本记录仅将实际检查到的客户端行为用于生成，不能外推为所有 stable 版本。

- `mania-manager.cs:537–546` 使用整数音符判定时间；691、724 将移动变换端点转为整数。同列不同高度的音符不能共用判定时间，否则重叠。H 行至少需要 H−1 ms，再加进出场边距，本生成器采用 H+1 ms。
- `timing-point.cs:36–49` 不对正红线 beatLength 使用 lazer 的 6–60000 ms 钳制。`mania-scroll.cs:66,109–114` 的固定滚速仍接受有效 BPM 和 SV；关闭 BPM scaling 不等于忽略变速点。
- `beatmap.cs:1470–1509` 按精确 double 分组，累计整数持续时间，求最常见 BPM；不会像 lazer 那样先将 beatLength 分组到 0.001 ms。当前 stable 曲线保持所有快慢红线互异，使开场的 500 ms 红线仍为参考。
- `native-settings.cs:647,959` 的 `CustomFrameLimit` 整数绑定默认 240、下限 60、上限 999；1428–1447 用整数解析后应用上下限。`native-bindable-number.cs:47–55,63–70` 设置界限会立即钳制当前值；`native-game.cs:1035–1038` 的 Custom 模式使用该值。因此 30 实际变成 60，29.97 解析失败回退默认值。上一版 30 FPS 建议已撤销。[官方自定义限帧步骤](https://osu.ppy.sh/wiki/en/Performance_troubleshooting#custom) 说明配置入口，具体界限来自本机版本。

## 列数

支持完整的 1–18 列，包括 11、13、15、17。`beatmap.cs:912–916` 将 mania CircleSize 限制在 1–18；`native-mania-stage-manager.cs:1010–1012` 直接取谱面列数。`native-skin-main.cs:448–465` 在没有对应配置时新建 `SkinMania(CS)`；`native-skin-mania.cs:90–107,221–235` 按实际列数创建数组并提供默认贴图。因此 [skin.ini 文档](https://osu.ppy.sh/wiki/en/Skinning/skin.ini) 列出的皮肤配置键列表不是谱面列数白名单。

原版默认对大于 9 列分成两个舞台：`native-mania-stage-manager.cs:359–361,407–410,913–928`。11 列为 6+5，13 为 7+6，15 为 8+7，17 为 9+8。增加列数不保证形成无间隙的单幅矩形；实际布局与像素比例仍受皮肤影响。没有生成或强制专属皮肤。

## 为什么不能保证零过渡

普通音符由分段有限速度连续滚动。24 行旧曲线的最短完整换帧为 25 ms，60 FPS 的间隔约 16.67 ms，任何稳定刷新相位都无法跳过所有这样的换帧。单纯降低视频采样 FPS 只减少换帧频率，不会缩短每次下落。

诊断 `build/stable-diagnostics/refresh_phase_probe.py` 从实际序列化的普通音符 `.osu` 重新解析控制点并积分。两帧 6 列×24 行图案在 2094 ms 同时出现两帧的音符；60、144、240 FPS 均存在合法的相位采到此时刻。任意较低 FPS 也存在这样的相位，故改变间隔不能强制相位避开快段。谱面没有设置渲染时钟或让整幅画面瞬移的接口。

## 本次修复：实际刷新时钟与长条

### 可复现问题与边界

原算法并非逐帧累加舍入；问题是用整数游戏 FPS / 固定采样周期代表非整数显示时钟。回归将 20 FPS 的 2400 个变化帧按 `60000/1001 Hz` 采样，能在展示窗口之外采到切帧，60 秒之后仍会出现。此负对照保留；不能把用户全部残影归因于刷新率偏差，也未证明相位能被静态谱面锁定。

旧 lazer 每个重复画面都重新切换；现在两种客户端均在保守漂移预算内复用相邻相同画面，主动空档不合并。lazer 的复用预算还限制为参考 658 px 舞台上的 0.5 px，以免静态帧长期缓慢移动。不是直接删掉源帧或在预览中隐藏换帧。

### 排帧规则

- 新参数为 `refresh_hz`、`refresh_phase_ms`；旧 `game_fps` 仅兼容旧项目，两者互斥。桌面和 CLI 接受小数或分数刷新率；相位不超过正负一个刷新周期，音轨仍只按原开始时间延迟。
- 令实际刷新率 R、T=`1000/R`、分频数 D=`max(ceil(R/60),1,round(R/请求FPS))`。实际视频 FPS 为 R/D；所有边界直接从索引与分数周期推导，不把 R 或周期取整后递推。
- 切帧预算 C 必须小于 T，边距 M=`(T-C)/2`。第 i 个新画面的到位时刻为 `开始+相位+i*D*T-M`，stable 向下取整，lazer 保留小数；首帧不减 M。稳定展示结束为下一帧到位减 C。旧 `game_fps` 继续使用原来的整数边距，保持老项目行为。
- stable 仍保守限制行数 `min(请求高度,floor(T)-3)`，为整数端点和舍入留余量；lazer 不作该行数压缩。关闭新开关时按原请求采样。修改客户端、时间、滚速、模式、尺寸或清场设置会移除不再可靠的排帧元数据。

### 长条规则与有效快段

仅合并同一画面、同一列的一段连续 `#`；底部行成为头、顶部行成为尾，孤立亮格保留短音符。`.osu` 使用 type 128 和合法的 endTime；默认开关为 false，旧 JSON 没有该字段时仍按单键处理。当前开关不同于已经撤销的专属参考长条模式。

stable + 极速清场时，收集所有实际头尾和孤立音符的行，给每个不同端点分配 1 ms，再加末尾 1 ms 清场；预算未用部分继续近静止，真实移动推迟到 `sweep_start_ms`。24 行整列由 24 个短音符变为 1 个长条时，有效快段从 25 ms 缩至 3 ms；交错图案未必缩短。lazer 不改变其合法快段下限。桌面和 HTML 均按头尾跨度裁剪，头越过舞台后尾部仍可见，不按判定时间提前隐藏。

## 历史整数游戏 FPS 生成策略

1. 用户输入游戏渲染 FPS G 和请求的视频 FPS、列数、行数。G 必须是本机支持的 60–999 整数。
2. 刷新间隔 T=`1000/G` ms。实际行数取请求行数与 `floor(T)-3` 的较小值，使 H+1 ms 的完整换帧和两端至少各 1 ms 能放入一个间隔。G>250 时无法容纳一行及边距，提示降低游戏 FPS；列数保留。
3. 视频 FPS 调整为 G 的整数分频，分频数为 `max(ceil(G/60), 1, round(G/请求FPS))`。这样采样 FPS 不超过 60，每次变化对应整数次目标刷新。FFmpeg 使用实际尺寸和 FPS，选帧预览走同一条处理路径。
4. 对第 i 个采样边界 B=`原开始时间+i×1000/实际FPS`，完整新画面在 `floor(B−M)` 到位，其中 M=`max(1,floor((T−(H+1))/2))`。前帧于该时刻减去 H+1 ms 开始退场。首帧开始取原开始时间的向下整数，音轨延迟保持原值。
5. 普通音符整数曲线采用每行 1 ms，并按位置反算红线和 SV；快红线互异且为正，SV 保持合法范围。慢红线使用互异的大 beatLength，减少漂移。重复画面复用同一组音符，空场及帧间空档保留。

例如 G=60、请求 18×24、10 FPS，实际为 18×13、10 FPS，完整切帧 14 ms。请求 29.97 FPS 时实际为 30 FPS。请求、实际转换参数与 G 保存到 JSON v2 项目，导出附带 `播放设置.txt`。改变游戏滚速或编辑时间后仍须重新核查；调整采样 FPS/尺寸需要重新导入。
